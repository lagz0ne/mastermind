1 Environment = box recipe

Question. Should Mastermind read a repo's .devcontainer/devcontainer.json instead of its own recipe?

Mastermind today
  • packages/core/src/environment.ts: image, tools (baked and cached by hash), setup, check, limits (cpu, memory, timeout), network (open or allow list), repo, ref, requires, secret NAMES, provider login, output (pr, branch, none), instructions.
  • Stored in NATS KV, edited on /environments, one recipe per name, not in the repo.
What others do
  • Dev environment products (Codespaces, Ona) READ devcontainer.json.
  • Agent products (Copilot agent, Codex cloud, Claude Code on the web) use their OWN recipe. None of their docs mention devcontainer.json.
  • devcontainer.json has no network policy, no secret values, no time limit and no output.

Where we match, where we differ

  • Match: our split "tools = baked into a cached image, setup = each box" is the same split as Codespaces prebuilds (onCreate/updateContent cached, postCreate per instance) and the Claude and Codex setup caches.
  • Match: secret NAMES in the recipe, values elsewhere: same as Codespaces "secrets".
  • Differ: our recipe lives in Mastermind, not in the repo. Copilot keeps it in the repo; Claude and Codex keep it in the product, like us.
  • Differ: we have check (must pass before the agent starts) and output. Nobody else has a separate check; Copilot stops at the first failing setup step, which gives the same effect.
  • Risk if we read a repo's file: devcontainer.json can change the HOST, not only the box: initializeCommand (spec: runs "on the host machine"), runArgs (--privileged, --network=host), mounts, privileged, capAdd, securityOpt, dockerComposeFile. Codespaces runs them on a throwaway VM; our runner runs on the user's own machine.
  • Gaps in the spec: no egress property; hostRequirements are MINIMUMS ("minimum required number of CPUs"), not limits; no output.

Human direction, 2026-11-12: clone the repo (check that it can be cloned first), then use the repo's devcontainer config, or an environment definition in the same format. Bead mm-210.62. That follows Codespaces and Ona. My first draft said "keep our own recipe" (the agent products do that); I changed the recommendation below.

changeUse devcontainer.json as the format. Our fields in customizations.mastermind. Clean the config before the CLI sees it.
What
(1) git ls-remote --exit-code <repo> <ref> first ("Exit with status 2 when no matching refs are found"), then a shallow clone into the box workspace. (2) Find the config: the environment's own devcontainer.json, else the Codespaces locations, else the default box image. (3) Clean it: drop initializeCommand; reject (environment not ready, with the reason) or strip runArgs, mounts, privileged, capAdd, securityOpt, appPort; no dockerComposeFile in v1; inject our network in runArgs. Run devcontainer up --override-config <clean file>; --prebuild for the cached layer. (4) customizations.mastermind: secrets (union with the Codespaces top-level "secrets"), network, limits, output, provider, instructions, check. hostRequirements only as a readiness check.
Why
The human's direction; Codespaces and Ona prove the flow; repos that already have a devcontainer.json work without a second recipe. customizations is the spec's place for "product specific properties". The cleaning step is needed because the official CLI runs initializeCommand on the host every time.
Cost
One large bead (mm-210.62): runner (clone, find, clean, CLI), doctor/readiness reasons, /environments editor, migration of the current recipe fields.

2 Box per task

Mastermind today
  • apps/runner/src/box: one Docker (or Podman) container per task on the runner machine; image cached by recipe hash; limits; deleted after.
  • Allow list: internal network with no route out + a proxy box (CONNECT and plain HTTP, 403 for unlisted hosts).
  • The same network rule applies to setup and to the agent. Secrets are env vars and files for the whole box life.
What others do
  • One sandbox per task is the norm: Actions ephemeral runners, Codex and Claude (a VM per task or session), Copilot (an Actions job).
  • Egress = an HTTP(S) proxy with a domain allow list, wildcards, a package-registry preset.
  • Setup has more network than the agent (Codex: on for setup, off for the agent by default; Copilot: the firewall covers only the agent's Bash tool).

Where we match, where we differ

  • Match: one throwaway box per task, deleted after; HTTP(S) proxy with a host allow list and *.host. That is the common design. No official page says any of them uses iptables instead UNCERTAIN.
  • Differ: hosted products use a VM per task; we use a container on the user's machine. A container shares the host kernel. gVisor is the cheap middle step and needs no driver change beyond --runtime.
  • Differ: our setup gets the same network as the agent. Others give setup more (package registries) and the agent less.
adoptKeep the box. Adopt two network phases and an optional gVisor runtime.
What
(a) network gets a setup part and an agent part: setup may reach a "package registries" preset plus the list; the agent gets only the list (Codex default). (b) Environment field runtime: "runsc"; doctor checks that the runtime is installed. (c) Optional, later: a "read only" switch (GET/HEAD/OPTIONS) in the proxy, as Codex has.
Why
The agent phase is where prompt injection and exfiltration happen (Codex, Copilot docs). Setup needs registries; the agent mostly does not. gVisor closes most of the gap to a VM for little work.
Cost
Two small beads in the runner (proxy reload between phases; one Docker flag + doctor step). No server change.

3 Worker onboarding and readiness

Mastermind today (mm-210.59)
  • runner onboard <token>: local checks, enrol with a single-use token (valid 24 h), ask for missing secrets, doctor --deep, then READY.
  • States onboarding, checking, ready, degraded. Re-check every 5 min. Status lists the ready environments.
  • The server gives work only to a runner whose last status is ready, younger than 2 min, and lists the item's environment.
What others do
  • A short-lived enrol token becomes a long-lived runner credential (GitHub 1 h token or JIT config; GitLab token made in the UI first, shown once; Buildkite agent token gives a session token, then a token per job).
  • "Not ready" = send no new work; it does not kill the worker (Kubernetes readiness, NoSchedule taint).
  • A runner that is gone for long becomes stale and is removed.
ProductOnboarding, labels, healthSource
GitHub self-hosted runnerRegistration token "expires after one hour"; ./config.sh --url --token --labels --ephemeral. Status Idle / Active / Offline. config --check reports PASS/FAIL per service. Removed after 14 days without connection; a runner below the minimum version gets no jobs.adding runners, monitoring, removing
GitLab RunnerCreate the runner in the UI or API first, get a glrt- token (shown once), then gitlab-runner register --token. Old registration tokens can be turned off (410 Gone). Status online (contact in the last 2 h), offline, stale (more than 7 days), never_contacted. Paused runners keep their registration but take no jobs.docs.gitlab.com: new creation workflow, runners scope

Hook pre-bootstrap can reject a job before it runs. Health endpoint --health-check-addr: /agent/<n> 500 if the last heartbeat failed.buildkite.com: tokens, hooks, monitoring

Where we match, where we differ

  • Match: single-use token to a long-lived service-account credential (GitHub, GitLab, Buildkite). Ready / degraded = Kubernetes readiness (stop new work, keep running). Our per-environment readiness is like Buildkite's pre-bootstrap gate, but decided before the offer.
  • Match: our doctor = GitHub config --check, with a deeper end-to-end run.
  • Differ: our enrol token lives 24 h (KV mm_tokens); GitHub's lives 1 h.
  • Differ: the live runner list forgets a runner after 24 h without status (apps/api/src/people/registry.ts), but its service account (the credential) stays valid with no stale or remove rule.
keepKeep the model. Add a stale and remove rule, and a shorter enrol token.
What
Service accounts of runners: offline (no status for 2 min, what the gate uses now), stale (no status for 7 days, GitLab), flagged and then disabled after 14 days (GitHub removes such runners). Runner enrol token: 1 h (GitHub); the person who enrols runs the command at once anyway.
Why
The model already is the common one. The lifecycle stops unused runner credentials from staying valid for ever. A shorter token lowers the risk of a leaked onboard line.
Cost
One small bead (a timer in the api, a column in /people, one TTL).

4 Dispatch and routing

Mastermind today
  • packages/router: ordered rules put an item on a named queue, or offer it to one address with a fallback queue.
  • Runners pull (next); a waiting runner gets a wake-up. req:<capability> labels: the runner must have every one.
  • Pick: priority, then age. Claim = lease of 5 min with heartbeat; release on expiry.
  • No attempt counter. No fairness between accounts on one queue.
What others do
  • Workers pull with a long-poll wait (Temporal, JetStream, SQS).
  • Lease = timeout + explicit extension (SQS visibility, JetStream AckWait + in-progress, Temporal heartbeat timeout).
  • A cap on redeliveries, then a dead-letter queue or an advisory.
  • Fairness by a tenant key on one shared queue.
ProductRouting, leases, fairnessSource
GitHub Actionsruns-on labels are cumulative: the runner needs all. A matching idle runner that does not pick the job up within 60 s: the job is queued again. No match: it fails after 24 h.docs.github.com: self-hosted runners
BuildkiteNamed queue (queue= tag) plus tags that must all match. Concurrency groups across pipelines.buildkite.com: queues, concurrency
TemporalWorkers poll task queues, only with spare capacity. Sticky queue falls back to the normal queue after 5 s. Timeouts: Schedule-To-Start, Start-To-Close, Heartbeat. Priority 1-5 plus fairness keys (per tenant, weighted round robin, per-key rate limits).docs.temporal.io: task queue, activity timeouts, priority and fairness
NATS JetStreamWork-queue retention: the first ack removes the message. AckWait default 30 s; in-progress ack resets it; MaxDeliver then an advisory (no built-in DLQ). MaxAckPending 1000.docs.nats.io: acknowledgment, retention
AWS SQSVisibility timeout (default 30 s), extended with ChangeMessageVisibility ("a heartbeat mechanism"), max 12 h. Redrive to a DLQ after maxReceiveCount. Fair queues (2025): a MessageGroupId per tenant; a noisy tenant does not delay the others.visibility timeout, DLQ, fair queues

Where we match, where we differ

  • Match: pull model with a wait (Temporal, SQS); named queue + capability labels that must all match (Buildkite queue + tags, GitHub group + labels); lease with heartbeat (SQS, Temporal); direct offer with a fallback queue (Temporal sticky queue, GitHub 60 s re-queue).
  • Match: we do not need JetStream work-queue retention: our items are records, not messages, so the stream keeps them (see 5).
  • Differ: no attempt limit. An item whose runner dies again and again goes back to the queue forever. Every system above caps it.
  • Differ: one account with 50 items can delay everyone else on a shared queue. Temporal and SQS solve this with a tenant key.
adoptKeep the model. Add a maximum of attempts. Add fairness per account later.
What
(a) Count claims per item; after N (for example 3) lease expiries or failures, the item goes to a "needs a human" state with the reasons (SQS maxReceiveCount, JetStream MaxDeliver). (b) When two or more accounts share a queue: pick round robin by the account that created the item, then priority, then age (Temporal fairness keys).
Why
(a) stops a poison item from using all runners. (b) stops one account from starving the others. Both are standard.
Cost
(a) small: a counter on the item, one router check, one board state. (b) medium: change selectBead in packages/router; do it when a second account shares a queue.

5 Work store on NATS JetStream, files on Object Store

Mastermind today
  • packages/work: stream MM_WORK, one subject per item, file storage, 1 replica; every write is a compare-and-set on the item's last sequence.
  • KV for accounts, routing, environments, leases. Object Store for files (mm-210.60, 128 KiB chunks).
  • deploy/nats/nats.conf: sync_interval: always, explicit limits. Backup: stream snapshots + manifest (mm-210.36, apps/api/src/backup).
What NATS docs say
  • R1: "If that server goes down, the stream goes down with it." R3 is "the production floor".
  • Default sync_interval is 2 min; always syncs every write, slower.
  • "R3 is availability, not a backup." Test restores: "A snapshot you never test is a guess."

Where we match, where we differ

  • Match: file storage, sync_interval: always (stricter than the default), CAS on every write, an event log per item with derived state: this is the pattern Synadia describes. Snapshots with consumers, a manifest and restore: the documented backup path.
  • Differ: R1 on one Dokploy host. The docs call R1 risky in production. A lost disk = lost work since the last backup.
keepKeep NATS as the only store. Treat R1 as a known risk with three guards.
What
(1) Backups go to a target OFF the NATS host. (2) A scheduled restore test into a scratch server (the docs say an untested snapshot "is a guess"). (3) Back up the auth/operator config with the streams. Move to R3 when three servers in separate failure domains exist; the stream config already sets num_replicas, so it is a config change plus a cluster.
Why
One host cannot give R3. Off-host backups plus tested restores give a known recovery point now.
Cost
Small. Most of it is in mm-210.36; the restore test is one schedule.

6 Credentials into the box

Mastermind today
  • Git: a fine-grained personal access token (GIT_TOKEN, GITHUB_TOKEN or GH_TOKEN) or an SSH deploy key, from the runner's local secrets (apps/runner/src/box/output.ts).
  • The token is in the box for the whole run, readable by the agent. The push runs in the box after the agent.
  • Claude: a token from claude setup-token as a box secret.
What others do
  • Short-lived, narrow tokens from a GitHub App, not a person's token.
  • The real credential stays OUT of the agent's reach: Claude web swaps a scoped credential at a proxy; Codex removes secrets before the agent phase; Copilot "cannot directly run git push".
  • Push only to one agent branch (Copilot: copilot/).

Where we match, where we differ

  • Match: secret values stay on the runner machine, never on the server (box decision B). Push to a branch per item (mm/<item>), PR opened for review: same shape as Copilot and Claude.
  • Differ: we use a person's token that lives for days or months (30 days by default); all others use a 1 h app token.
  • Differ: our agent can read the git token and push anywhere the token allows. Copilot, Claude web and Codex keep the real token out of the agent's reach.
  • Open point for the human: each user puts their OWN setup-token on their OWN runner. That looks like "CI and scripts" use. Mastermind does not offer a claude.ai login. But the Agent SDK sentence above is broad, and we cannot confirm how it applies here UNCERTAIN.
changeUse a GitHub App token per task, kept out of the agent's reach. Make an API key the first choice for Claude.
What
(1) A GitHub App (one per Mastermind install, or the user's own app) with Contents + Pull requests on the chosen repos. For each task, mint a token for that ONE repo, valid 1 h. Extra repos: customizations.mastermind.repositories, the same shape as Codespaces, shown in readiness. The access check (ls-remote) uses the same credential. Never put the git token in --secrets-file. (2) The agent phase gets no git token: the runner pushes after the agent ends (like Copilot), or a git credential helper / proxy outside the agent's process gives it only for mm/<item>. Add branch protection on the base branch. (3) The environment UI shows ANTHROPIC_API_KEY first and CLAUDE_CODE_OAUTH_TOKEN as "your own subscription, your own risk". Keep the PAT path for other git hosts.
Why
A leaked PAT gives write access to all its repos until it expires (30 days by default). A leaked app token gives 1 h on one repo. This is what GitHub itself recommends and what every agent product does.
Cost
Medium: about 2 beads. Who holds the app private key (Mastermind server or the user's runner) is a design decision for the human; my pick is the runner owner's machine, the same as other secrets (decision B).

7 Login by single-use code

Mastermind today (mm-210.28)
  • POST /api/auth/login/start gives a code ABCD-EFGH (8 of 32 symbols, 40 bits, no 0/O/1/I), valid 10 min, plus a cookie.
  • An APPROVER (operator CLI, or a logged-in account on /people) types the code; the approver sees the browser's user agent and the code's age.
  • The browser polls GET /api/auth/login/poll: pending, expired or approved (session cookie). Code entry is rate limited. No "deny".
What others do
  • RFC 8628 (device flow): the DEVICE shows the code; the SAME user, signed in elsewhere, types it.
  • Admin approves a device: Tailscale (an admin approves a new device; until then it cannot send traffic). WhatsApp: the trusted phone scans the new device's QR code.
SourceFactLink
RFC 8628Response: device_code, user_code, verification_uri, expires_in (required), verification_uri_complete, interval (default 5 s). Poll errors: authorization_pending, slow_down (+5 s), access_denied, expired_token. User code: base-20 BCDFGHJKLMNPQRSTVWXZ, 8 chars, about 34.5 bits, rate-limit attempts. 5.4: tell the user they authorize a device; keep the code short-lived.rfc-editor.org/rfc/rfc8628
GitHub device flow"8 characters with a hyphen in the middle", expires_in 900 s, slow_down adds 5 s, 50 code submissions per hour per app.docs.github.com: device flow

WhatsApp linked devicesThe new device shows a QR code; the trusted phone scans it after a biometric or PIN check.faq.whatsapp.com

Where we match, where we differ

  • Match: same shape as RFC 8628 and GitHub (short code with a hyphen, short life, polling, rate-limited entry). Our code is stronger (40 bits vs 34.5) and shorter-lived (10 vs 15 min).
  • Differ, on purpose: in the RFC the user approves their own device. In ours a different person approves, because the new user has no other session yet. That is Tailscale's device approval, not RFC 8628. So copying the RFC exactly gives no gain.
  • Differ: no deny (RFC access_denied), no slow_down. Our states have their own names.
keepKeep the flow. Add Deny. Use RFC names only when a CLI logs in.
What
(1) The approver can Deny a code; the browser shows "denied" (access_denied). (2) Keep showing the approver what they approve (browser, age; add the IP country if cheap), per RFC 5.4. (3) If the runner or a CLI ever logs in as a human, implement RFC 8628 names and polling rules (interval, slow_down), so standard clients work.
Why
The flow already follows the prior art that fits (admin approval). Renaming the browser API gives nothing to users now.
Cost
Small: one bead for Deny. The RFC names only with a CLI login.
