Mastermind: the box

Review document, 2026-11-11. Source: your message "the dispatcher will need to run the box and then run the task inside, not the other way around". Red marks the box and the decisions.

1 The change

Today the runner starts a Paseo agent directly on the user's machine, in a work directory. The agent sees the whole machine. Tools, permissions and secrets are whatever that machine has.

New: for each task, a fresh box is made from the task's environment. The agent runs inside the box. Only the result leaves the box. Then the box is thrown away.

DispatchMastermind gives the task and its environment to a runner.
Make the boxFrom the environment image: tools already in it. Limits on CPU, memory, time, network.
Fill the boxCheck out the repo at the ref. Put in the secrets and the provider login. Run setup and check.
Run the taskPaseo daemon in the box starts the agent. No permission prompts: the box is the limit.
Take the result outReports and the answer go to Mastermind. Code goes out as a pushed branch or a patch.
Throw it awayThe box and all in it are deleted. Also on failure or timeout.

3 The environment becomes a box recipe

type Environment = {
  name: string;
  // the box
  image: string;        // base, e.g. ghcr.io/getpaseo/paseo
  tools: string[];      // baked into a cached image
  setup: string[];      // per box, after checkout
  check: string[];      // must pass before the agent starts
  limits: { cpu: number; memoryMb: number;
            timeoutMin: number };
  network: "open" | { allow: string[] };
  // what goes in
  repo: string; ref: string;
  secrets: string[];    // names only
  provider: { name: "claude"; auth: string }; // a secret name
  // what comes out
  output: "branch" | "patch" | "none";
  instructions?: string;
};
  • Tools are built into an image one time and kept by the hash of the recipe. A box starts from that image in seconds.
  • Setup runs in each new box: install the repo's dependencies, seed data.
  • Check proves the box is ready. A failed check ends the task with the reason; no agent starts.
  • Permissions are the box limits. Inside, the agent runs with no prompts, so the start failure from today cannot happen.
  • Network: open, or a list of allowed hosts.
  • Provider login is one more secret, for example a Claude token, so the box needs no login by hand.

4 Your decisions

A. Where do boxes run?

1. On the runner machine (recommended first)Podman or Docker on the user's machine. The user brings the compute, as now. No new cost for Mastermind.
2. On box hosts that Mastermind runsA pool of machines (for example Dokploy or a VM service). A user needs no machine. Mastermind pays the compute.
3. Both, behind one interfaceA "box driver": local first, hosted later. Same environment recipe for both.

My recommendation: build the driver interface now (3), with the local driver (1) first.

B. Where do secret values live?

1. On the runner machine (recommended first)The user's runner keeps the values. They never reach Mastermind. Each user sets their own.
2. In MastermindEncrypted store per account. Set one time, used by all runners and hosted boxes. Mastermind holds the key.
3. BothMastermind for shared, team secrets; runner for personal ones (like the provider login).

My recommendation: 1 now. 2 is needed for hosted boxes (A2), so it comes with them.

C. How does code leave the box?

1. Push a branch (recommended)mm/<item-id> to the repo, with a deploy key secret. The ticket links to it. A pull request is optional.
2. A patchThe diff goes to Mastermind and shows on the ticket. A human applies it.
3. NothingOnly the answer text. For tasks that are questions, like your first ticket.

The environment chooses with output. A task can always also have the answer text.

D. Is direct run (no box) still allowed?

Today's mode, agent on the machine, is useful for a trusted machine and for tests. Recommendation: keep it as a runner setting that is off by default (--no-box), and show on the ticket when a task ran without a box.

6 Worker readiness (mm-210.59, 2026-11-12)

Your rule: a worker gets jobs only after its checks pass. The client owns onboarding; Mastermind checks it again.

onboardingonboard has not finished. Connected, reports, takes no work.
checkingFirst checks run after start: Paseo, providers, workdir, box engine, secrets.
readyGets work, only for the environments whose own checks pass (every needed secret present).
degradedA re-check failed (engine gone, Paseo down). No work. Ready again when the checks pass.
WhoEnforces
Runnermastermind-runner onboard <token>: local checks (no credential) → enroll → missing secrets (hidden prompt) → doctor --deep → READY. Stops at the first FAIL with the fix. Then it asks next and accepts offers only in ready, for ready environments only. Re-check on start and every 5 min.
DispatcherGives work only to a runner whose last status is ready, less than 2 min old, and lists the item’s environment. Else next answers {notReady: [reasons]}. A runner that lies stops getting work when its status goes stale.

7 The box from devcontainer.json (mm-210.62, 2026-11-12)

Your rule: clone the project, make sure it can be cloned, then use its devcontainer. Prior art: GitHub Codespaces and Ona (clone, then read the repo’s devcontainer.json); the Dev Containers spec; the official @devcontainers/cli. The review is in docs/design/prior-art.html, section 1.

access checkgit ls-remote with the environment’s credential only. Fails: reason on the ticket, no box.
find configOwn config, configPath, .devcontainer/devcontainer.json, .devcontainer.json, else default image.
cleanHost fields removed (initializeCommand, runArgs, mounts, privileged...). No Compose.
builddevcontainer build (CLI 0.90.0 through the runner’s Bun), then the Mastermind layer (Paseo, Claude). Cached by config hash.
boxOur driver: limits, network. Clone, lifecycle commands from the image metadata, setup, check, agent.
DecisionWhy
Build with the CLI, run with our driverdevcontainer up makes the container with host mounts and runArgs, and always runs initializeCommand on the host. devcontainer build does not run it (tested with 0.90.0), and our driver keeps the limits, the network and the cleanup.
Lifecycle from the devcontainer.metadata labelThe CLI writes the merged config of the features and the file there (spec: image metadata). We run onCreate, updateContent, postCreate and postStart in the order of the spec, as the remoteUser.
initializeCommand only when the environment allows itThe spec runs it on the host. Codespaces runs it on a throwaway VM. We run it on the user’s machine, so the owner must list it in devcontainer.allowHost.
Secret namescustomizations.mastermind.secrets are required. The top-level secrets (Codespaces) are recommended: a missing one is listed, it does not block.
Image with its own image fieldAn environment with an image and no devcontainer settings keeps the old recipe. Set devcontainer.use: none to never use one.

Not in v1: Docker Compose, feature entrypoints and privileged features (docker-in-docker), Alpine images, network phases (open for setup, allow list for the agent).

8 Code by mount (mm-210.83, 2026-11-12)

Your rule: the outer side clones and pushes; the box works on a mounted copy. Prior art: GitHub Actions container jobs (actions/checkout runs on the runner host, the job container mounts the workspace). The runner keeps one clean clone per repo on its machine and fetches the ref with the environment’s credential. Each task gets a fresh work copy, mounted at /workspace: the box gets no git credential and does no clone. After the agent, the runner reads the work tree as data, against the base, with a temporary index of the clean clone. The copy’s .git (config, hooks, refs) is never used. It makes one commit on the base and pushes mm/<item> from the clean clone. The work copy is deleted with the box on every exit path. Rootless Podman and Docker are handled by giving the copy to the box user before the agent and back after it. MM_BOX_CODE=clone keeps the older way (clone in the box, bundle out). Measured on vite with rootless Podman: the code is in the box about 2 s sooner, and reading the changes takes about 2 s longer. The total is the same. The gain is the credential, not speed.
